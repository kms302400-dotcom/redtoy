# 상품별 배송 후 7일 자동 완료 및 적립

## 범위와 기준

현재 `od_status='배송'`인 주문을 대상으로 한다. 운영에서 사용자가 확인한 981건을 그대로 강제 완료하는 기능은 아니다. 실제 실행 시점의 배송 주문을 모두 분류하고, 상품별 조건을 충족한 주문만 완료한다. 이미 완료된 과거 주문은 신규 대상에 포함하지 않는다.

- 취소·반품·품절 상품행은 제외한다.
- 정상 상품은 모두 배송 또는 완료 상태여야 한다. 준비·주문·알 수 없는 상태·NULL이 하나라도 있으면 보류한다.
- 정상 상품 **모두**의 `ct_invoice_time`이 정상적인 한국시간 날짜여야 한다. 누락·0일시·잘못된 날짜·미래 날짜는 보류한다. 주문 전체 `od_invoice_time`으로 대체하지 않는다.
- 정상 상품의 가장 늦은 배송일시로부터 7×24시간이 지난 주문을 완료한다. 한국시간 기준으로 판단한다. 택배사 배송추적 완료일을 조회하지 않는다.
- 정상 상품이 없는 주문은 보류한다. 기존 완료 상품과 취소·반품·품절 상태는 유지하고 배송 상품만 완료로 바꾼다.
- 주문일 제한은 기본적으로 없다. 기존 `--from` 옵션을 명시하면 여전히 주문일 제한을 적용하므로 운영 cron의 과거 `--from=2026-07-21T15:00:00`은 제거해야 한다.

## 포인트와 중단 복구

- 완료된 해당 주문에 대해서만 기존 `insert_point()`와 `@delivery / 회원ID / 주문번호,ct_id` 관계를 사용한다.
- `@member / 주문번호 / 상품구입` 결제 적립 이력이 하나라도 있으면 해당 주문의 추가 적립을 보류한다. 이력 삭제·중복 지급을 하지 않는다.
- 이미 `@delivery` 이력이 있는 상품은 제외한다. `ct_point_use` 표시값보다 실제 이력을 우선한다.
- 신규 적립은 저장된 `ct_point × ct_qty`이다. 비회원·탈퇴 회원·포인트 비활성 설정에는 지급하지 않는다. 회원 레코드가 남아 있어도 `mb_leave_date`가 비어 있지 않으면 신규 지급과 재시도에서 제외한다. 배송 완료 처리는 유지한다. 취소 상품에는 지급하지 않는다.
- 지급은 기존 수동/배치 지급 함수와 같은 `redtoy_save_order_point` DB 잠금을 사용한다.
- 주문 완료 UPDATE와 함께 기존 `od_mod_history`에 `[redtoy-auto-complete:v2]` 처리 기록을 추가한다. 완료 후 지급 전 중단되면 다음 실행에서 이 기록이 있는 완료 주문만 미지급 여부를 재검사한다. 일반적인 과거 완료 주문은 소급 지급하지 않는다.
- 기존 지급 이력을 삭제하거나 취소 회수 정책을 바꾸지 않는다. 금액만 부분환불하고 상품 수량/적립값이 그대로인 주문은 본 코드가 환불 비례액을 계산하지 않으므로 지급 전 별도 검토가 필요하다.
- 주문 상태 잠금과 포인트 잠금을 중첩하지 않는다. 외부 관리자 취소 경로 전체가 이 잠금에 참여하는 것은 아니다. 초기 누적분 복구는 관리자 동시 상태 변경이 없는 시간에 진행한다. MyISAM에서는 주문·상품·포인트 여러 테이블을 하나의 트랜잭션으로 원자 처리할 수 없으므로 완료 이력과 포인트 관계 이력을 통해 중단 복구한다.

## 파일

- `www/adm/shop_admin/order_auto_complete.php`: 기존 CLI 코어 파일 수정. 상품별 평가, 완료 후 적립, 재시도, 집계 출력. 웹 common.php·세션·방문 기록·extend·PG 코드를 부팅하지 않는다. 지급에는 기존 공통 포인트 함수와 최소 의존 라이브러리를 사용한다.
- `www/lib/redtoy_order_completion.lib.php`: 신규 레드토이 전용 날짜 판단·조회·처리 함수.
- `tests/redtoy_order_completion.php`: 격리된 로컬 DB와 합성 데이터만 사용하는 테스트.

DB 스키마 변경은 없다. 실제 적용 시 기존 주문 상태, 정상 상품 상태, 상품 판매수량, 포인트 이력/잔액, 주문 변경 이력과 작업 로그가 갱신된다.

## 검증

PHP 8.4.24 / MariaDB 12.3.2에서 InnoDB와 MyISAM 모두 테스트한다. 운영 DB 설정은 로드하지 않는다. 임시 테스트 DB 이름은 매번 난수로 만들고 종료 후 삭제한다.

```sh
REDTOY_COMPLETION_TEST_SOCKET=/private/tmp/redtoy-completion-db.XXXXXX/db.sock \
  /opt/homebrew/opt/php@8.4/bin/php -d short_open_tag=1 tests/redtoy_order_completion.php
```

최종 결과: 113개 검증 통과. 변경 PHP 3개 문법 검사와 변경 범위 공백 검사 통과.

검증 항목: 정확히 7일/1초 전, 마지막 상품 날짜, 취소·반품·품절 제외, 미배송·빈값·0일시·잘못된 날짜·미래 날짜, 기존 완료 상품 혼합, 주문 헤더 날짜 무시, 오래된 주문, 실제 공통 포인트 함수/회원 잔액, 결제 적립·완료 적립 중복 제외, 표시값 불일치, 비회원, 탈퇴 회원의 조회·완료·지급·재시도 제외 및 완료 후 탈퇴 재검사, 적립 비활성, 미지급 중단 복구, 지급 실패 후 복구, 주문/지급 잠금, 실제 CLI 반복 실행, 조회 모드의 상태·포인트·파일 미변경, 합성 배송 주문 981건의 전체 집계와 100건 처리 한도.

## 운영 반영 전

아직 운영 적용·cron 수정·실제 주문 완료·실제 포인트 지급을 수행하지 않았다. 운영 최신 소스와 변경 파일의 일치 여부를 다시 확인한다. 기존 main 작업 트리의 다른 미커밋 정책·리뷰·알림 변경을 배포에 섞지 않는다. 마지막으로 확인된 운영 Git 브랜치는 `codex/rollback-pg-keep-selected`이며 운영 작업 트리에는 별도 적용된 변경이 있다.

1. 기존 두 cron을 백업하고 일시 중지한다. 운영 파일과 관련 주문/장바구니/상품/포인트/회원 테이블을 백업한다. DB 엔진에 맞는 일관된 백업 방법을 선택한다.
2. 개발 검증 결과 리뷰 후 새 CLI/라이브러리 2개만 배포한다. 파일 권한과 PHP short_open_tag 설정을 확인한다.
3. 새 코드의 `--dry-run`으로 현재 배송 주문 전체의 대상·보류 사유·신규 지급 예상액을 다시 확인한다. 기존 헤더 기준 890건/375,260P를 그대로 사용하지 않는다.
4. 운영 반영 전 이 조회 결과를 사용자에게 보고하고 누적분 처리 승인을 받는다. `--dry-run`은 설정·상태·포인트 UPDATE, 잠금/로그 파일 생성 없이 조회만 수행한다. config.php와 dbconfig.php만 읽는다.
5. 승인 후 제한된 크기의 첫 배치를 검증한다. 기본 `--limit=100`, 최대 1000이다. dry-run의 `eligible`/`preview_points`는 한도와 무관한 전체 적격 합계이며 `planned_completions`만 실행 한도를 표시한다. 이전 실행에서 미지급된 자동 완료 주문의 재시도 예상액은 `preview_recovery_points`로 별도 표시한다. 실행 시 적격 여부와 적립 이력을 다시 조회하므로 예상액은 실제 데이터 변경에 따라 달라질 수 있다.
6. 새 자동 완료 작업이 완료와 지급을 함께 처리한다. 기존 `order_complete_point.php` 별도 작업은 동시에 재개하지 않고, 보정 목적과 대상 범위를 별도 검토한다. cron 로그 경로를 실제 존재하는 `/home/user/redtoy/www/data/`로 수정하고 과거 `--from` 제한을 제거한다.
7. 실행 주기에 따른 지연이 있다. 예: 서버 UTC 00:00 일일 실행은 한국시간 09:00이며, 7일 도달 후 최대 다음 일일 실행까지 기다린다. 더 짧은 주기는 운영 정책으로 선택한다. 등록된 CLI PHP 경로·시간대·로그/잠금 쓰기 권한을 확인한다.
8. 정상 주문 하나와 결제 적립 주문 하나에서 완료 상태·원본 이력·추가 적립/중복 제외·회원 잔액을 확인한다. 다음 실행에서도 중복 지급되지 않는지 확인한다. 외부 PG 테스트는 이 작업에 필요하지 않다.

### 롤백

먼저 새 cron을 중지하고 실패 지점을 확인한다. 코드만 기존 CLI로 복구해도 이미 완료된 상태/지급액은 원복되지 않는다. 기존 DB 전체 복원은 이후 발생한 주문/포인트를 덮어쓸 수 있으므로 사용하지 않는다. 이 작업의 완료 표식과 포인트 관계 이력을 대조해 해당 주문만 별도 검토한다. 이미 지급한 포인트를 자동 삭제/회수하지 않는다. 새 라이브러리는 호출하지 않는 상태로 남겨도 무방하다. 운영 DB 원복과 포인트 회수는 추가 승인을 받아 수행한다.

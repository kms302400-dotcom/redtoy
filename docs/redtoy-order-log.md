# 레드토이 주문내역 로그

후아몰 `/Users/moosugkim/Documents/Codex/hooamall`의 `miyamall-domain-cleanup` 브랜치에 있는 orderlog.php/hooamall_order_log.lib.php와 checkout 연결을 분석했다. 이전 안내 경로는 이동되어 현재 등록 프로젝트 경로에서 확인했다. 주문 수정 감사 로그가 아니라 주문서 진입부터 주문 처리 완료까지의 진행 관측 기능이다.

## 기능

주문내역 바로 아래 메뉴 400405 ‘주문내역 로그’를 추가한다. 날짜/주문번호 검색, 50개씩 페이지 이동, 회원/비회원, 파트너, PC/모바일, 진입 당시 선택 상품/옵션/수량, 마지막 단계 및 전체 단계 시각을 보여준다. 저장된 주문만 관리자 주문 상세 링크를 제공한다. 접수된 주문의 현재 입금/취소 상태와 파트너는 실제 주문에서 읽는다. 서버 세션의 파트너 값은 진입 시 참고값일 뿐 귀속을 새로 설정하거나 검증하지 않는다.

선택 상품은 서버 장바구니에서 ct_select=1인 행 최대 100개를 최초 진입 시 저장한다. 이름/옵션은 255자, 상품번호는 20자로 제한한다. HTML 출력은 이스케이프한다. 원문 POST, 고객 이름/연락처/주소, 회원 ID, IP, User-Agent 원문, PG 응답·인증정보는 기록하지 않는다. 주문번호는 개인정보와 연결될 수 있는 운영 식별자이므로 관리자 권한을 제한한다.

기록 단계:
- entered: 서버에서 주문번호 발급 뒤 선택 장바구니 스냅샷.
- submitted: 기존 세션 주문번호가 있는 다날 준비/PC·모바일 주문 처리 요청의 서버 도착.
- payment_ready: 다날 카드/휴대폰 준비 처리의 기존 성공 응답. 결제창이 실제 열렸다는 뜻은 아니다.
- payment_confirmed: 기존 주문 처리의 검증을 통과하고 거래번호와 실제 입금액이 있는 상태. 무통장 주문 접수는 여기 포함하지 않는다.
- order_saved: 주문 INSERT 확인과 장바구니 갱신의 기존 실패 처리 분기를 통과한 뒤. 이후 쿠폰/알림 등 후속 처리와 구분한다.
- completed: 기존 주문 후속 처리와 알림톡 호출이 반환된 뒤. 알림 전달 성공을 보증하는 이벤트가 아니다.
- save_failed 및 오류 분류: 기존 저장 실패 분기와 alert 훅에서 고정된 오류 분류만 기록. 오류 원문은 저장하지 않는다. 치명적 PHP 오류도 원문 없이 failed로 기록한다.

레드토이는 후아몰의 checkout_attempts 토큰 구조가 없으므로 요청값의 주문번호를 사용하지 않고 기존 ss_order_id를 따른다. 여러 주문 탭 때문에 기존 시스템의 세션 주문번호가 바뀌는 한계는 동일하며 이를 수정하지 않는다. 브라우저 내부 검증, 네트워크 단절, 닫힌 결제창은 서버에 도착하지 않으면 기록할 수 없다. 별도 세션만 여는 기존 danal_cancel.php는 공통 훅을 실행하지 않아 취소 반환 단계는 새로 연결하지 않았다. 실제 접수된 주문의 취소는 주문의 현재 상태로 표시한다. 후아몰의 장바구니 변경/만료 토큰 이벤트와 텔레그램 주문 로그 알림도 이식하지 않았다.

새 단계 없이 주문이 저장되지 않은 채 1시간이 지나면 ‘이탈 추정’으로 표시한다. 승인·완료 단계가 있는데 주문이 없으면 ‘확인 필요’다. 기존 단계는 소급 복원하지 않는다. 동일 주문번호·동일 단계는 UNIQUE 키로 최초 1회만 기록하며 재전송은 최초 상품/시각을 덮어쓰지 않는다.

## 권한과 DB 작업

조회는 400405 읽기 권한, 선택 삭제/90일 이전 정리는 삭제 권한과 관리자 CSRF 토큰을 검증한다. POST 외 변경은 없다. 선택 삭제는 최대 50개 주문번호의 모든 단계만 지운다. 실제 주문/장바구니는 수정하지 않는다. 진행 중인 주문의 로그를 삭제하면 이후 단계가 새로 기록될 수 있다.

최근 90일만 조회하며 오래된 자료는 자동 삭제하지 않는다. ‘90일 이전 로그 정리’는 POST로 최대 1,000행씩 삭제한다. 후아몰의 GET 시 삭제와 웹 요청 CREATE/ALTER는 가져오지 않았다.

별도 테이블 `실제접두사_redtoy_order_log` 하나를 InnoDB로 추가한다. 기존 테이블 ALTER/데이터 갱신은 없다. PK id, UNIQUE(order_id,event), created_at 인덱스가 있다. 운영 주문 od_id가 unsigned bigint인 점에 맞춰 로그 주문번호를 CAST하고 주문의 PK를 보존하는 조인을 쓴다. 인증정보/도메인/PG 설정은 후아몰에서 복사하지 않았다.

## 적용·복구

1. 기존 운영 브랜치는 마지막 확인 기준 codex/rollback-pg-keep-selected. 개발 소스 공급 브랜치와 혼동하지 않는다. 변경 범위와 적용 충돌을 먼저 검사한다.
2. 기존 shop/orderform.php, shop/orderformupdate.php, mobile/shop/orderformupdate.php를 비공개 폴더에 백업한다. 신규 파일/로그 테이블이 이미 있으면 중단하고 별도 백업·구조 확인을 한다. 신규 테이블 생성만 하므로 기존 주문 DB를 복원할 작업은 없다.
3. 실제 접두사를 확인하고 migration.sql.example을 별도로 실행한다. SHOW INDEX/SHOW CREATE TABLE로 구조를 확인한다. 테이블이 없다면 로그 기록은 실패하되 주문은 계속되므로 DB를 먼저 반영한다.
4. lib/redtoy_order_log.lib.php → extend/redtoy_order_log.extend.php → 관리자 페이지와 기존 코어 3개 순서로 배치한다. 코어 호출은 function_exists로 보호된다. PHP 문법/Apache 설정 검사 후 재로드한다. 기존 CRLF 줄바꿈을 유지한다.
5. 최고관리자 화면을 확인하고 부관리자는 새 메뉴 읽기/삭제 권한을 설정한다. 실제 업무 주문서 진입 이후 로그와 상품/기기 표시, 정상 주문 링크 및 기간 필터를 확인한다. 배포 검증만을 위해 실제 PG/알림 API를 호출하지 않는다.
6. 복구는 기존 코어 3개를 먼저 되돌린 뒤 새 extend/관리 페이지/라이브러리를 제거한다. 로그 테이블은 보존한다. 완전 제거가 필요할 때만 비공개 덤프 후 별도 승인하에 DROP TABLE 실제접두사_redtoy_order_log를 실행한다. 주문·회원·결제 DB를 백업으로 덮어쓰지 않는다.

코어 3개 변경 이유: 번호 발급 및 주문·상품 저장 성공 이후를 확정하는 훅이 없어 해당 지점에 기록 호출만 추가한다. 금액/승인/취소/재고/포인트/쿠폰/파트너 처리 자체는 바꾸지 않는다. 현재 PC/모바일 공통 주문서 외 구형 모바일 처리 파일에도 연결한다. 코어 업데이트 시 호출 위치를 다시 확인해야 한다.

## 성능·검증

일반 쇼핑몰 요청은 추가 SQL이 없다. 주문서 진입에 선택 상품 조회 1회와 INSERT 1회, 실제 단계별 INSERT 1회가 추가된다. 로그 실패는 false로 반환하고 외부 API나 재시도를 수행하지 않는다. 로그 조회 SELECT에는 MariaDB의 개별 쿼리 1초 제한이 적용된다. 테이블 잠금·DB 연결 자체의 지연까지 무지연을 보장하지는 않는다.

격리 로컬 MariaDB에서 46개 검증: 기록/중복/상품 선택, XSS, 서버 세션 주문번호, 메뉴/읽기·삭제 권한, CSRF, 잘못된 선택, GET 비파괴, 실제 주문 보존, 페이지 이동, 기기/파트너, 단계/현재 상태, 조회 제한, 테이블 누락과 실패를 확인했다. 합성 MyISAM 주문 20,000건/로그 80,000행의 첫 페이지 PHP 렌더링은 약 41ms였다. 네트워크/실제 관리자 헤더를 포함한 운영 응답시간은 아니다.

기존 입금 126개·다날 취소 180개·배송완료 123개·결제 포인트 56개·금액 표시 24개 검증도 통과했다. 전역 DB 잠금을 공유하는 취소/배송완료 테스트는 병렬 실행 시 충돌하여 순차 재검증했다. 실제 운영 DB/PG/알림 API는 호출하지 않았다.
